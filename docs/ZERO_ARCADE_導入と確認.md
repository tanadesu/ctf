# ctf / ORBIS FRONTIER のユニコインQR連携

## 引き分けの確定ルール（2026-10-14）

引き分けは両者に5,000枚ずつ、合計10,000枚を付与します。共有資料の「引き分け未定・空欄」に対し、この決定を優先します。

運営adminの「ユニコイン」→「ZERO ARCADE連携」→ ctfの「設定を編集」で、引き分けの付与枚数に `5000` を入力し、保存してください。この値は1人分です。勝ち `10000`、負け `0`、上限 `10000` はそのままです。

ゲームは2人それぞれのplayIdで同点のスコアを送信し、APIが返す5,000枚と本人専用QRを表示します。枚数をゲーム側で上書きしたり、同じQRを共有したりしません。設定後、422が表示されていた結果画面は「QR取得を再試行」で取得できます。管理画面の設定変更と実API確認は未実施です。

## 実装した動き

Firebase Hostingはゲーム画面、RenderのNodeサーバーは対戦と報酬APIを担当します。ブラウザ → 認証済みのゲームサーバー `/api/reward` → ZERO ARCADE admin の順で通信します。ブラウザからadminには接続しません。

2人がそろい、サーバーの `phase` が `ended`、`elapsed >= C.duration`（現状900秒）のときだけ発行します。途中の「ゲーム終了」では結果のみ表示します。

ルーム作成時のランダムUUID・再戦世代 `epoch`・本人IDで `playId` を作ります。送るJSONは `{playId, points, opponentPoints}` のみです。スコアはサーバーで確定した本人と相手の火星輸送人数を使います。ブラウザから送られた得点、勝敗、本人ID、playIdは使用しません。本人はセッショントークンで特定します。ゲームIDや会社名もadminへ送りません。

終了時に2人分の得点を固定し、本人が結果画面を開いた時に本人分を発行します。2人とも自分の結果画面を開くと、それぞれ別のplayIdで処理します。失敗時は同じIDと両得点で再送します。同時要求は1件にまとめ、成功結果は再表示・再読み込みで再利用します。最初の通信でadmin側だけ処理が成功した場合も同じplayIdで再試行するため、admin側の重複排除を利用できます。

APIの `coins` と `outcome` はゲーム側で再計算しません。画面は本人の枚数・PNGの `qrImageDataUrl`・有効期限を表示します。QR内容をリンクへ変換せず、`qrPayload` はブラウザへ返しません。0枚は画像なし、422は「付与数確認中」、未設定・通信障害・不正な応答は案内と再試行ボタンです。結果・勝敗・財務集計はQR発行とは別に、先に表示します。相手のQRは共通snapshotや操作履歴へ含めません。

## 変更ファイル

- `arcade-rewards.js`：サーバー専用。終了判定、得点固定、発行、キャッシュ、同時送信集約、タイムアウト、応答検証。
- `server.js`：ルームUUID、終了検知、本人専用 `/api/reward`、画面モジュールの配信。
- `reward-ui.js`：本人の枚数・QR・期限・再試行、古い試合から遅れて届く応答の無視。
- `game.js`：結果モーダルへの組み込みと途中終了の表示。
- `styles.css`：白地・余白付きの読み取り用QR表示。
- `scripts/build-hosting.mjs`：画面用モジュールだけを追加配信。サーバー専用モジュール・秘密変数・`.env` は含めません。
- `render.yaml`：秘密変数の名前のみ宣言し、報酬テストをビルド時に実行。
- `.env.example`：値が空のローカル設定例。`.env` は既存の `.gitignore` で除外済み。
- `test/arcade-rewards.test.js`、`test/reward-ui.test.js`、`test/network.test.js`：発行・表示・認証・2人対戦の確認。
- `README.md`、本書、共有された2資料：導入・差分・制限の説明。

## ローカルで起動する

Node.js 24を使用してください。ゲーム本体に依存パッケージ追加はありません。

まず、実際の報酬を発行せずゲームを確認できます。

```sh
npm start
```

`http://localhost:3000` を独立した2つのブラウザで開きます。会社名入力 → ルーム作成・参加 → 両者準備完了で開始します。キー未設定でもゲームは動き、完走後は連携未設定の案内になります。

本物のAPIへ接続する場合は、`.env.example` を `.env` にコピーし、エディターで2項目の値を登録します。コマンドやチャットへキーを貼り付ける必要はありません。

```sh
cp .env.example .env
# エディターで .env に運営から受け取った値を入力して保存
node --env-file=.env server.js
```

`npm start` は `.env` を自動読込しません。シェル等で環境変数を設定済みの場合は `npm start` でも使えます。実APIで完走すると本物の報酬が発行されるため、運営指定のテスト環境で確認してください。

## 自動確認

```sh
node --test test/arcade-rewards.test.js test/reward-ui.test.js
NETWORK_TEST=1 node --test test/network.test.js
npm run build:hosting
```

10件の報酬・表示テスト、2件のローカル通信テストを確認済みです。通信テストはローカルポート3097・3098を使います。報酬通信はテスト用応答に置き換え、実際のadminを呼びません。テスト内だけ試合時間を短縮し、本番の900秒は変更しません。

確認内容：自然終了、途中終了拒否、未認証拒否、クライアントの偽スコア無視、2人別ID、本人専用応答、0枚、422、障害、タイムアウト、同時8要求の集約、失敗後の同一データ再試行、再戦・別ルーム、新旧応答の分離。

`npm test` 全体には従来からの旧仕様テスト3件の失敗が残っています（物流拠点必須、宇宙港の再建設、開始建物が1つという期待）。今回のコードは現行のゲーム仕様を維持しています。全テスト成功とはしていません。

## Renderで秘密設定を登録する

1. Render Dashboardで **orbis-mars-api** を選びます。
2. 左メニュー **Environment** → **Environment Variables** → **Add Environment Variable** を開きます。
3. 次の2項目を登録します。
   - `ZERO_ARCADE_API_URL`：運営から指定された完全な `https://<adminホスト>/api/arcade/rewards`。末尾のAPIパスまで含めます。
   - `ZERO_ARCADE_API_KEY`：ctf専用に発行されたキー。Firebase側には登録しません。
4. **Save, rebuild, and deploy** を選択します。コードが未反映なら先に次のデプロイ手順を実施してください。

値を `render.yaml`、HTML、JS、公開JSON、GitHub、スクリーンショットやログへ書かないでください。`render.yaml` の `sync: false` は値をコードに持たず、設定画面で入力するための宣言です。既存サービスでは上記画面から追加してください。

公式手順：https://render.com/docs/configure-environment-variables

## デプロイ手順

1. この作業フォルダーの変更ファイルを `tanadesu/ctf` の対象ブランチへコミットします。`.env` は含めません。`arcade-rewards.js` と `test/arcade-rewards.test.js` を忘れるとサーバーの起動・ビルドに失敗します。
2. Renderが参照するブランチへ変更を反映し、秘密変数を設定します。サービスの **Manual Deploy → Deploy latest commit**、または設定保存時の再デプロイで起動します。
3. Renderでデプロイ成功を確認してから、画面をFirebaseへ反映します。

```sh
npm run build:hosting
npx firebase-tools deploy --only hosting --project ctf1-99feb
```

4. `https://ctf1-99feb.web.app` を再読み込みし、2人で完走します。勝敗・財務の下に「あなたのユニコイン」が出ます。APIの枚数が正の場合はQRと期限が表示されます。
5. ZERO ARCADEアプリのウォレット →「スキャン」で読み取り、残高と履歴が1回だけ増えることを確認してください。通常のカメラで開くURLではありません。

この作業フォルダーには `.git` がないため、ローカルのブランチ名・コミットは確認できません。GitHubへの反映と本番公開は別作業です。本番デプロイ・秘密変数登録・実APIの受取確認は未実施です。古い `render-upload.zip` 等には本変更が入っていないので使わないでください。

## 共有資料と現行コードの違い

リポジトリ内になかった同名2資料をDownloadsから読み、`docs/` にコピーしました。ctfのAPI指示と現行コードの構造は一致しています。参照先の `ZERO_ARCADE_API.md` 自体は見つからず、2資料に記載されたリクエスト・応答形式を使用しました。

READMEには「宇宙港を建設」「物流拠点完成後に参入」「オフライン前提」とありますが、現行コードは宇宙港が10番区画に配置済みで、物流拠点なしで市場参入できます。Render + Firebaseで公開する構成も存在します。ゲームの現行動作を優先し、READMEの関連記述を修正しました。QRの自動発行にはadminへ接続できるインターネット回線が必要です。

ctfにhanbai/locketの中継サーバーやVercel設定を混ぜていません。他2ゲームはブラウザ計算のため単なる中継では偽スコアを完全防止できず、別リポジトリでサーバー検証またはスタッフ確認が必要です。
